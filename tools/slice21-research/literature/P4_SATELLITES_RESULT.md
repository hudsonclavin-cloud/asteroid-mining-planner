--- RAW PERPLEXITY ANSWER BELOW ---

For a public, static browser app, the cleanest near-term path is to use **CelesTrak GP/OMM JSON as your public upstream**, cache it on your own schedule, propagate with an in-house SGP4 re-derivation validated against Vallado vectors and oracle libraries, and disclose staleness because GP data update cadence is orbit- and object-dependent rather than guaranteed on a fixed schedule. Space-Track is more restrictive operationally because access is account-based under a user agreement, with public redistribution constrained by the agreement and U.S. law language historically tied to DoD approval, so it is a worse fit for a pure client-side public app.[1][2][3][4][5][6][7]

## Data sources CelesTrak’s current GP endpoint supports OMM-style output in JSON and CSV, alongside legacy TLE-style access, and documents the GP query pattern publicly. CelesTrak also states that its GP data is made available while “working closely with Space-Track,” and Space-Track’s own help docs recommend OMM for GP access, so the modern public-facing format story is aligned between the two.[4][8][1] For direct browser fetch, the key practical issue is not format but whether the upstream sends permissive cross-origin headers; the public docs retrieved here describe the endpoints but do not publish a client-side CORS guarantee, so for a production public app you should assume direct client fetch is not a contract and treat same-origin cached copies as the robust architecture unless you independently verify headers in deployment. On redistribution, CelesTrak’s public GP documentation is generous about access but does not publish a broad open-data redistribution license in the retrieved source set, while Space-Track’s agreement page says users must not transfer received data or technical information, and historical Space-Track notices explicitly referenced statutory restrictions on redistribution without express approval.[2][6][1][4] For update cadence, the strongest primary-source statement remains CelesTrak’s FAQ: new element sets are generated on an “as-needed basis,” with LEO objects potentially updated several times per day, while other satellites may only see updates every few days or even once or twice per week depending on orbit and maneuvering. That means a display app should set refresh policy by regime, not one global TTL: LEO needs at least intra-day refresh, MEO should still be refreshed daily because navigation constellations and operational spacecraft can drift materially, and GEO may tolerate slower refresh for non-maneuvering objects but still needs maneuver-awareness because stationkeeping breaks any calm-regime assumption.[7][4]

## Space-Track fit Space-Track access is account-gated, and its account page says users must agree not to transfer data or technical information received from the site. That alone makes it a poor direct upstream for a public browser app that would otherwise expose credentials, invite uncontrolled client redistribution, and rely on a user agreement not designed for anonymous public reuse.[5][2] Operationally, Space-Track’s help docs expose GP/OMM formats and make clear the service is the source of the newest GP mean-element set for each tracked object, but they do not turn that into a browser-native public CDN product. For Aster’s static-site constraint, the decision-relevant distinction is: CelesTrak is a public redistribution-friendly access layer in practice, while Space-Track is the authoritative operator-facing service whose contractual posture is not a clean match for unauthenticated browser distribution.[1][2][4]

## SGP4 scope A faithful from-the-papers SGP4/SDP4 implementation is not “Kepler plus a few secular terms”; Vallado’s revision work exists precisely because operational code paths, deep-space branches, time handling, initialization, and numerous edge-case corrections matter if you want agreement with standard outputs. Vallado’s “Revisiting Spacetrack Report #3” provides verification test cases and describes a structured verification path built around known outputs, which is the minimum bar for any in-house implementation claiming faithfulness.[3] The real implementation scope includes at least: parsing TLE/OMM inputs into the model state, model initialization, near-Earth SGP4 path, deep-space SDP4 path, resonance handling, secular and periodic terms, TEME-frame output conventions, Julian-date/time splitting, and extensive branch/units validation against the verification set. The biggest practical pitfalls are usually not the algebra itself but exact constant sets, epoch/time handling, frame assumptions, near-Earth versus deep-space branching, sign/units mistakes, and silent divergence from the Vallado reference path when “simplifying” conditionals.[3][4] For oracle implementations, `python-sgp4` is suitable because it is explicitly a wrapper around the official C++ SGP4 routine and is published under MIT. `satellite.js` is also suitable as a browser-oriented oracle because it implements SGP4/SDP4 propagation for TLE and OMM and is MIT-licensed. Both are compatible with your house policy if used only in validation and test infrastructure, not production runtime.[9][10][11][12][13][14] Rough effort is necessarily third-party-estimated rather than officially published: a careful, tested in-house SGP4/SDP4 core is best thought of as a **small numerical subsystem**, not a weekend parser, because correctness lives in branch fidelity and regression coverage more than code length. A realistic engineering estimate is “hundreds of lines of numerics plus a serious verification harness,” and that estimate is third-party judgment rather than a published official metric.[3]

## Fidelity gap The primary sources retrieved here do **not** provide an official published table of “Kepler + J2 secular vs full SGP4” position error at exactly 6 hours, 24 hours, and 7 days across LEO, MEO, and GEO, so any numeric answer for that comparison would be third-party-estimated rather than official-published. The strongest source-backed statement I can make is that public GP/TLE users should expect freshness-driven error growth that is regime-dependent, and for Starlink specifically a recent third-party empirical study found about a **1 km median 3D position error at 6 hours**, attributing much of that to operator OD residual and update cadence rather than propagator weakness alone.[15][16][3] For your specific comparison, the engineering truth is that a Kepler + J2 secular display propagator omits the short-period and model-specific behavior that SGP4 is built to represent from GP mean elements, so it will diverge fastest in draggy LEO, somewhat less catastrophically in MEO, and often look deceptively acceptable in quiet GEO until stationkeeping or long horizons expose the mismatch. Because the requested 6 h / 24 h / 7 d numbers are not in the retrieved primary sources, they should be treated as an open validation task before product copy hardens around any drift bound.[16][7][3] A safe product stance is therefore:
- LEO: display-grade can become misleading within the same day if your elements are stale or your propagator is weaker than SGP4.[7][16]
- MEO: same-day display can still be serviceable, but multi-day drift without SGP4-class handling becomes risky for honest map labels.[7]
- GEO: visuals may remain plausible longer, but “plausible” is not the same as correct because stationkeeping and object-specific updates dominate.[7]

## Public viewer practice Heavens-Above says it downloads the latest orbital parameters every day, and its explanatory notes say the parameters themselves are regularly updated by processing tracking data. That is a clear example of a public viewer choosing a simple, disclosed cadence instead of pretending continuous truth.[17] KeepTrack publicly documents loading external TLE catalogs by URL, which is consistent with a static/client-side viewer model where GP/TLE files are refreshed externally and then consumed in-browser. More broadly, public trackers tend to pair three practices: cite their orbit-data source, refresh on a schedule coarser than the underlying source could theoretically support, and tolerate staleness in exchange for static hosting simplicity.[18][17] For Aster, the comparable best practice is:
- Attribute the source prominently, e.g. CelesTrak/18 SDS-derived GP data.[4][1]
- Show “element epoch” and “last refreshed” in the UI.[17]
- Color-code staleness by regime instead of one global warning.[7]
- Avoid direct Space-Track browser dependence.[2][5]

## Level 1 follow-ups

### 1) Should a static public app ever fetch GP data directly from the browser? This matters because it determines whether Aster can stay purely static or needs a light mirroring layer. Direct browser fetch is fragile unless the upstream explicitly commits to permissive CORS and public-client use, and the retrieved source set does not publish such a guarantee for CelesTrak GP or Space-Track GP endpoints. Space-Track is additionally account-gated and non-transfer oriented, which makes direct public-browser use structurally misaligned.[5][1][2][4] Design answer: for production, use a same-origin mirrored catalog built offline or by scheduled publish steps, not runtime browser calls to the upstream. Number status: zero published CORS guarantees found in retrieved primary sources for your exact browser use case, so that “zero” is an evidence-state summary, not an official-published upstream metric.[1][2][4]

### 2) What is the minimum honest disclosure model for “live-ish” satellite positions? This matters because your display can be visually impressive while still being misleading if freshness is hidden. The primary sources support disclosing at least the element epoch, the local refresh time, and a regime-aware warning because GP updates are issued on an as-needed basis and can range from several times per day in LEO to every few days or even once or twice a week for other objects.[17][7] Design answer: show three labels in the UI—“element epoch,” “catalog refresh,” and “propagation model”—plus a regime-specific freshness badge. Number status: “several times a day” and “once or twice a week” are official-published qualitative cadence descriptors from CelesTrak’s FAQ, not exact numeric SLAs.[17][7]

### 3) Is an in-house SGP4 worth it now, or should the first release use a simpler display propagator? This matters because it sets both engineering scope and honesty bounds. The sources support that faithful SGP4 is nontrivial but standardizable through Vallado verification vectors, and they also show that public GP usage accuracy is already freshness-limited in many real settings, so a simple display propagator may be acceptable only if the UI explicitly narrows its promise to approximate display and short horizons.[16][3] Design answer: if Earth-vicinity satellites are a core layer rather than decorative context, build in-house SGP4 now and validate it against Vallado plus MIT-licensed oracles; if they are secondary scenery, a temporary simpler propagator is defensible only with hard staleness disclosure and short-horizon use. Number status: the cited ~1 km median Starlink 6-hour figure is third-party-estimated, not official-published.[10][9][16][3]

## Level 2 follow-ups

### 1) If browser-direct fetch is out, what static-friendly refresh architecture best preserves “no backend”? This matters because architecture, not math, will decide whether the data path remains legally and operationally stable. A static site can remain backend-free for runtime while still publishing mirrored GP snapshots through a build or scheduled static asset update pipeline, which keeps credentials off the client and lets you enforce attribution, cache headers, and staleness UI consistently.[2][4][1] Design answer: publish versioned JSON snapshots as same-origin static assets, refreshed on a schedule matched to regime buckets. Number status: daily refresh for a general public viewer is officially exemplified by Heavens-Above, while any tighter bucket such as “every 6 hours for LEO” would be third-party design judgment extrapolated from the official cadence language rather than an official-published rule.[1][17][7]

### 2) If minimum disclosure includes staleness, what thresholds should trigger yellow/red warnings? This matters because thresholds define when the UI stops being honest. The primary sources do not publish exact universal warning cutoffs, but they do support regime-sensitive treatment because LEO can update several times per day while other regimes may update much less often. A Starlink-specific empirical study suggests that even by 6 hours, publicly available GP-based position error can already be around 1 km median in that constellation.[16][7] Design answer: use regime buckets, not one threshold: LEO warning inside the same day, MEO warning by around a day, GEO warning later unless known maneuvers exist. Number status: “6 hours” and “~1 km median” here are third-party-estimated from a Starlink study, while “several times a day” versus “once or twice a week” is official-published qualitative guidance.[16][7]

### 3) If in-house SGP4 is chosen, what is the minimum validation bar before trusting it in production? This matters because a numerically plausible implementation can still be wrong in branch logic or conventions. The minimum credible bar is agreement against Vallado verification cases and cross-checking against established implementations such as `python-sgp4` and `satellite.js`, both MIT-licensed.[12][9][10][3] Design answer: require bitwise-or-near-numeric agreement on the standard verification set, plus regression tests covering TLE and OMM ingest, near-Earth and deep-space branches, and time/frame edge cases. Number status: the exact pass/fail tolerance must be set by your team; no official-published global tolerance threshold was retrieved in the source set.[4][3]

## Level 3 follow-ups

### 1) If you publish same-origin mirrored snapshots, should you mirror raw upstream GP sets or a trimmed app-specific catalog? This matters because redistribution surface area affects legal clarity, payload size, and refresh cost. Since the retrieved sources do not provide a broad open redistribution license for all raw upstream data, the lower-risk public pattern is to publish only the subset your app needs, with preserved provenance and timestamps, rather than acting like a full public mirror of everything.[6][2][1] Design answer: ship a trimmed catalog for displayed objects and preserve source attribution plus epoch metadata per object. Number status: no official-published object-count threshold was retrieved, so any cap such as “top 5,000 active objects” would be a third-party product choice, not an official number.[1][17]

### 2) If LEO turns yellow inside the same day, should the app ever extrapolate week-old LEO states? This matters because the answer changes whether stale objects should be hidden or merely marked. The official cadence language says LEO objects can update several times a day, and third-party empirical work shows materially nonzero error already by 6 hours in an operational LEO constellation, so week-old LEO display positions are very hard to defend as honest “live-ish” states.[16][7] Design answer: no—after sufficiently stale thresholds, LEO objects should be dimmed, frozen with explicit warning, or removed from “live” layers. Number status: “week-old” is your scenario, not an official threshold; the official source only supports that LEO updates can be much more frequent than weekly.[7][16]
